# 项目记忆: pingpong-schedule 央视乒乓赛程刷新

## 单链滚动刷新机制(「轻量刷新」once 链)
- 全局同时仅 1 个 name 含「刷新」的 once 任务;旧链删除后再建新链,保证唯一。
- 每次运行:读 data.json → 并行采集(4组 subagent 扇出;降级则编排器自采) → 串行交叉认证 → 更新 data.json(只改 result/live/risk/time/channel/schedule;live 为进行中局分,result 优先于 live,保留四日期与昨日战报,subtitle 维持;**updatedAt 必须改为本次执行时刻**) → git add/commit/push(origin,gitee 已弃用) → 按「刷新时刻计算」新建下一个 once 并删除旧的。
- **【用户铁律】updatedAt 必须随每次刷新同步变更**:只要刷新 once 成功跑完,data.json 的 updatedAt 就改为执行时刻并推送;若更新后 updatedAt 与执行前相同,即判定本次刷新「静默失败」,必须立即补建下一跳 once 重刷,绝不允许留下「网页时间未变」的假象。网页「数据更新于」直接读 updatedAt,故时间不变=数据没真刷新。
- **【用户铁律·2026-08-17 18:07 追加/覆盖旧例】无数据变更时也必须 bump updatedAt 并推送**。用户原话:「无变更的话,也要显示时间变了,要不然我怎么知道你是不是干了活。」
  - 即:**每一次任务(主任务 8h 周期 + 刷新链 once)跑完都必须刷新 updatedAt + git push**,时间戳是「本次执行已发生」的凭证,不是「数据有变」的凭证。
  - **废止**先前做法(2026-08-17 09:46 / 17:44 两轮曾因「数据无变更」而不写 data.json、不 bump 时间、不推送)——那样用户无法区分「跑了但无变化」与「压根没跑/挂了」,体验上等同失败。
  - 诚实性怎么保:只 bump `updatedAt` + 在 `note` 里如实写「**本轮复核未发现数据变更**,按约定仍刷新时间戳」,**matches/schedule/result 一律不动、绝不伪造赛果**。诚实体现在 note 与 matches,不体现在「不刷时间」。
- 刷新时刻计算:赛前候选 T=K-1h(仅 T∈(now,now+30h] 入选);赛中候选整链只加 1 个 now+30min 轮询点;候选升序后 30 分钟聚类合并(≤30min 并入同簇取最晚,>30min 另起簇);取 ≥now+30min 最早簇为 T_next。无候选则不建(链暂歇,等 8h 主任务重新对齐)。
- **【凌晨场日期修正·重要坑】**:data.json 按「08:00~次日08:00」窗口归类,00:00-07:59 的场虽写在「今日」date 下,真实开赛日期是**次日**。计算 K 时须修正:若 match.time < "08:00",真实开赛日期 = 所属 date 的次日,K=次日+time;否则 K=date+time。若不修正,K 会落到过去,导致 00:00-07:59 这批场的赛前/赛中候选全部漏算、链在这些场开打前「假暂歇」漏刷。
- **赛中候选区间修正**:赛中候选判定由「已开赛(当前>K)」扩为「当前 ∈ [K-30min, K+3h]」(含开赛前30分钟),确保即将开赛的凌晨场也能被 now+30min 轮询点覆盖(否则 23:35 那跳算不出覆盖 00:00 场的下一跳)。
- next once: name=刷新链-[YYYYMMDD]-[HHMM]、modelId 必须 hy3、cwds=C:/Users/pengz/Documents/GitHub/pingpong-schedule(Windows 沙箱须用绝对路径;填无前导斜杠的 "Users/..." 会被误拼为 "C:/Program Files/WorkBuddy/Users/..." 致 once 跑错目录)、scheduledAt=ISO8601+08:00、prompt 完整照搬 FINAL 模板(含单链逻辑)。

## git 推送
- origin(github.com/pengzishang/pingpong-schedule)正常推送。
- gitee(gitee.com/pengzishang/pingpong-schedule)常因网络出口受限挂起:先 `git config http.lowSpeedLimit 1` 与 `http.lowSpeedTime 45`,再后台重试;仍失败留待下次主任务补推,不要无限等待。
- 提交信息格式:`赛程刷新_YYYY-MM-DD_HH:MM`。

## 数据约定
- days 四日期:昨日(带 result 战报)+ 今日 + 明日 + 后日。
- 未结束场 risk:以 🔴高风险 / ⚠️中风险 / ✅低风险 开头,括号大白话标签;⚠️ 另起一句写证据可靠性;📊 另起一句写人头对战;整段 2~3 句。
- 已结束写精简比分(含小分局分)。subtitle 固定「央视直播 · 乒乓球赛程 · 每日更新(可筛选 全部/国乒/日韩)」。
- live(进行中局分):该场已开赛且 result 仍空时由刷新链写入,格式与 result 完全一致——「选手A 大比分-大比分 选手B(已完局局分,/分隔)」,例「蒯曼 2-1 早田希娜(11-9/9-11/11-7)」;抓不到局分只写大比分;result 一旦写出即清空 live。前端 parseResult 同款正则消费,渲染为「🔴 进行中 · 当前比分」红横幅+比分表;前端每 60s 轮询 data.json 自动刷新 live。

## 【JSON 合法性硬检查·铁律】
- **改完 data.json 必须先 `python -c "import json;json.load(open('data.json',encoding='utf-8'))"` 校验通过才允许 commit。**
- 根因:`Edit` 工具 new_string 里写的 `\n` 有被落盘成**真实换行符**的风险。note 字段一旦混入真实换行,data.json 即为非法 JSON,前端 `res.json()` 直接抛 "Invalid control character",**网页停在旧数据、时间不变**。2026-08-16 02:45 那跳就是这样静默挂掉的(HEAD 版本已带病)。
- 修复法:定位 note 字段内真实换行/回车,全部转义为字面 `\n`。
- **「网页时间未变」有两个成因**:①updatedAt 没改;②**data.json 非法 JSON 导致解析失败**。第二个更隐蔽,只能靠 json.load 校验兜住,排障时两个都要查。
- 复杂转义别塞进 `python -c` + bash 单引号(会被二次转义弄乱),改写临时 .py 脚本执行后删除。

## 环境备注
- 央视EPG(api.cntv.cn)常失效、WTT官网 JS 墙、咪咕乒乓页 404、电视猫频道页需具体 slug;主要依赖新闻聚合(新浪/腾讯/网易/搜狐/今日头条/央视网)交叉确认。
- 单回合自动化无法回收后台 subagent 的 SendMessage 结果,采集走「编排器自采」降级路径更可靠。
- **失效源黑名单(别再优先试)**:sports.sina.com.cn/pingpang 返回404、sports.163.com/pingpang 返回404、s.weibo.com 站内搜索需登录、so.toutiao.com 搜索页只返回空壳导航。改用 WebSearch 间接命中这些站的正文最省时。
- **【AI幻觉赛果陷阱·必查】k.sina.com.cn(新浪看点)大量标注「本文由AI生成」的稿件会把「赛前预测」写成既成赛果**,例如 2026-08-15 02:13 那跳出现「张本智和3-0户上隼辅,三战全胜未失一局」,而该场 02:05 才开打、当时仅过 8 分钟,物理不可能。**采信任何赛果前必须做可行性校验**:开赛时刻 K + 局数×约8分钟 ≤ 当前时刻,否则一律判为幻觉并排除;见到「本文由AI生成」标记直接降权,不能作为交叉认证的独立源。
- **【跨赛事旧战报陷阱·必查】同一对阵在相邻两站重复出现时,旧站战报会被全网大量转载、极易误当本站赛果**。典型:「蒯曼4-1早田希娜(11-7/11-8/11-4/10-12/11-6)」实为 08-08 WTT横滨冠军赛,却在瑞典站同一对阵的 QF 搜索里霸屏(新浪/搜狐/腾讯虎扑/头条/so.html5.qq.com docid 页全都有)。**鉴别法**:核对稿件写的「下一轮对手」是否与本站签表一致(横滨稿写「半决赛对陈幸同」,瑞典站应为「对王曼昱」),再看教练细节与发布日期。
- **权威源优先级**:微博 @WTT世界乒联(uid 7556183438)发布的「男单/女单 X/8决赛 A 3-1 B【逐局】」是官方口径,单源即可写 result;虎扑(new.qq.com/rain 转载)+ 直播吧 + 腾讯新闻正文次之。
- **官方发布节奏可作「是否终局」判据**:@WTT世界乒联 与 @咪咕体育 一般在终局后 5~15 分钟内发逐局赛果。若某场开赛已超一小时而这两家都没发,基本说明仍在进行(而非漏抓),此时应保留 risk/live、绝不套用搜索里的同名对阵旧比分。
- **抓「进行中局分」最佳路径**:先用 WebSearch 找实时图文直播稿(腾讯搜索 so.html5.qq.com 转载的乒乓文字直播号,如「刘姚尧的文字城堡」逐分记录每局比分),再 WebFetch 对应 docid 页取最新一局;各体育站首页/频道页基本拿不到实时乒乓比分。
- 数据中 蒯曼vs早田希娜赛事 18:15 开打,但央视5于 18:00-18:30 播《体育新闻》,电视 18:30 才接播。

## 【真伪判定方法论·避免误杀】
- **单一平台多稿自相矛盾 ≠ 事件本身为假**。2026-08-29 14:16 那轮因新浪同日三稿互相矛盾(西安站/北京站/官方未公布)就把「邓亚萍杯」整体判为 AI 拼凑传言;22:16 轮追加跨平台复核(地方官媒「西安发布」、西安本地宝公众号、k.sina 两稿)后确认**赛事本体为真**,只是直播渠道未官宣。
- **正确判据分层**:①事件要素(时间/地点/奖金/阵容)多平台一致 → 事件为真;②仅「直播渠道/是否央视转播」未官宣 → 只影响是否写入数据文件,**不影响事件真伪**;③个别夸张细节(如「30 斤沙背心」)无出处 → 只剔除该细节,不连带否定整个事件。
- **处置原则**:事件为真但无央视转播、直播渠道未确认 → 仍**不写入** data.json/video.json,改为在 `note` 与早报留痕(八·乙同款),并显式注明「赛事为真、央视不转播」,避免下轮重复误判。
- **跨平台复核优先级**:地方官媒公众号/政务号(如西安发布) > 门户正文 > 门户聚合稿 > k.sina 看点/sports.sina.cn 服务性短文(这两处 AI 生成稿密度最高,只能作线索不能作独立源)。

## 【条件场作废机制·必查】
- 上一轮以「若 A 队取胜,则某日某时打下一轮」形式记载的条件场,**本轮必须先核查该条件是否已判定**:若 A 队已输球出局,条件场自动作废,必须**主动删除** data.json 对应日期 schedule 文案里的条件句 + 不写 video.json 该日期场次。
- 2026-08-29 22:16 轮即为此例:8/29 17:00 樊振东德国杯 1/8 决赛杜塞尔多夫 1-3 出局 → 8/30 21:00 的 1/4 决赛条件场自动作废,已从 data.json 8/30 文案与 video.json 中删除。**漏改会让外婆在电视前等一场根本不存在的比赛。**
- 删除条件句的同时,应在同段补一句**明确否定的话**(如「今晚 21:00 的比赛没有樊振东」),而不是静默删除——静默删除会让用户以为漏写。
