# 第 0 部分 · 结论

## 0.1 一句话

**这个项目不是「代码写坏了」，是「为一个用户写的需求，拿去服务另一个用户，51 天里没有人重新定义过一次目标」。**
重写的第一步不是写代码，是先把需求拆开、把数据契约结构化、把首屏还给外婆。

## 0.2 「全部重写」在本次计划里的准确定义

你说要全部重写。评审团的结论是：**重写，但不是把 2454 行重敲一遍**——那样会白扔两个月里唯一沉淀下来的正确业务判断（外婆只看央视、视频只在无央视日兜底、23:00 后重播归次日……这些不是代码，是知识）。

本计划定义的「全量重写」= 四件事同时做：

| # | 重写对象 | 做法 | 不是 |
|---|---|---|---|
| 1 | **需求文档** | PRD 拆成两份（早报 PRD / 网页 PRD），网页 PRD 从零重写 | 不是改 PRD 版本号 |
| 2 | **数据契约** | `data.json` 从「散文 + 关键词」升级为**显式结构化字段**，版本号冻结 | 不是加几个字段 |
| 3 | **前端** | 新目录、新模块划分、**删掉全部自然语言解析器**（约 1000 行） | 不是重命名变量 |
| 4 | **业务规则** | 以**规则清单 + 测试**的形式迁移，代码重写 | 不是复制粘贴 |

## 0.3 三个必须修正的根因（其余都是症状）

1. **用户错位**：PRD 的用户故事全部以「子上」为主语，网页产品的终端用户是「外婆」，两套需求从未拆分。PRD §6 五条成功指标**全是采集端指标**，没有一条衡量「外婆是否按时看上比赛」→ 所以过去 51 天、约 500 次提交里，没有任何一次能被判定为「做对了」。
2. **业务规则寄生在自然语言里**：前端靠正则解析采集端写的散文（`nextEvent.note` 的「出战:」段、`dayNote` 的「止步/出局」措辞）来做**判定**，而不是**展示**。采集端改一次句式，前端静默出错。
3. **数据侧能静默删除整场比赛**：`riskSaysNoTV`（`app.js:677-684`）只要 `risk` 文本命中「手机/APP/咪咕/央视频/不直播/只在.*播」等词，**该场次从页面彻底消失**，前端不报错、采集端不知道。**已实测复现**（§9.1）。

## 0.4 一个元结论

这个项目最贵的资产**不是代码，是判据**。574 次提交里真正有价值的是三类知识：

> **「什么样的数据不可信」「什么样的写法会打断前端」「什么样的动作会让双机同步崩」——这三类知识全部在 memory 里，而不在代码里。**

重写如果丢掉它们，等于把 52 天试错白付一遍学费。

**但同时要看清**：memory 里有相当一部分「判据」，本质是**前端解析器脆弱性外溢出来的写作规范**（§3.4.3）。它们是**症状的正确记录**，但**不是正确的解法**。重写要做的，是把这些「让人迁就代码」的规则，换成「让代码适应数据」的结构。

# 第 1 部分 · 现状还原

> 这一节是「参考代码和各种文件拼凑出的需求与细则」，作为重写的输入基线。

## 1.1 双产品，必须拆开

| | 产品 A：每日早报 | 产品 B：国乒赛事日历（网页） |
|---|---|---|
| 用户 | **子上**（本人） | **外婆**（老年用户） |
| 场景 | 早上 8 点要知道「今天央视转播什么、几点、哪个台」，且要能核验来源 | 打开手机看一眼「今天几点、哪个台」，到点开电视 |
| 核心诉求 | 信息可信度（≥4 源交叉认证、冲突留痕、证据可追溯） | 一眼看清（大字号、高对比、零动脑） |
| 载体 | WorkBuddy 会话推送 + Markdown 存档 | 静态网页（GitHub Pages） |
| 现有文档 | PRD v1.4 §1-§5.3（FR-1 ~ FR-14） | PRD §5.4 一个子节（FR-15a ~ FR-15n）——**从未独立立项** |

> **决策 D-1**：重写产出两份文档：`早报PRD.md`（保留 FR-1~FR-14，基本不动）与 `网页PRD.md`（全新，§4 即其骨架）。

## 1.2 网页产品的唯一任务链

```
① 打开页面  →  ② 看今天几点、哪个台  →  ③ 到点开电视
```

**第 ② 步是全部价值所在。** 任何不能加速第 ② 步的元素，都是噪音。

## 1.3 产品边界

**做**
- 央视（CCTV-5 / 5+ / 16）转播的乒乓球赛程
- 今日 + 明日 + 后日 的滚动窗口
- 已结束场次的比分（昨日战报）
- 空窗期「今天为什么不播 + 下一站是什么」
- 央视不播时的视频平台兜底（手机看）

**不做**
- 非央视渠道（咪咕/腾讯/优酷等）作为**主**内容
- 实时比分（外婆不边看网页边看球）
- 赛事预测、球员分析、评论
- 历史赛果数据库
- 多用户 / 订阅 / 个性化频道偏好
- 赛前 30 分钟提醒（子上 2026-08-06 已决定不做，D4）

**北极星**：外婆当天按页面信息成功看上比赛的场次比例（不可直接测量，用下列代理指标）。

## 1.6 采集侧现状（540 行 `采集说明.md`，自动化任务的唯一指令源）

# 第 3 部分 · 经验与判据库（重写护栏）

> 来源：前端机 `.workbuddy/memory/`（23 篇）+ 采集端 `pingpong-schedule/.workbuddy/memory/`（45 篇）+ 45 份 automation memory。
> 标注：【事实·可复现】= 记忆里有具体复现记录；【判据】= 项目已固化规则；【推断】= 主理人归纳。

## 3.1 工程与流程经验

### 3.1.1 ⭐ 用「数据字段的单调变化」当自动化的心跳

**【事实·可复现】** 项目铁律第 1 条：`updatedAt 必刷 + 写完即推送`。

- 每轮采集无论有没有新数据，**必须**把 `data.json` 的 `updatedAt` 改成当前时间并推送。
- 如果某轮跑完 `updatedAt` 没变 → **判定为静默失败**，必须立刻补建下一跳任务。
- memory 里出现几十次「`updatedAt` 19:05→19:50（静默失败铁律满足）」「`updatedAt` 02:17→02:48（铁律达成）」。

**【判据】** 无监控的自动化任务，需要一个**外部可观测的、单调变化的心跳**。`updatedAt` 就是这个心跳。

**【可迁移性】** 高。任何「定时任务 + 静态产出 + 无 APM」的场景都适用。

**【代价】** 不遵守 → 任务静默失败无人知晓（项目里真实发生过多次「磁盘已改、远端没推、网页时间没变」的失联）。

### 3.1.2 双机 Git 协作四铁律

**【事实·可复现】** 两机同推一个仓库，全程 574 次提交没丢过数据，靠的是四条：

| 铁律 | 做法 |
|---|---|
| **先拉后采** | 开始采集/读取数据前先 `git fetch origin && git rebase origin/main` |
| **写完即推** | `data.json` 通过校验后**立即** commit/push，早于早报/记忆/收尾动作 |
| **先拉后推** | 推送固定为 `git add → commit → fetch → rebase → push`（先固化再重放） |
| **禁强推** | 任何情况不得 `--force` / `--force-with-lease`；冲突保留刚生成的数据为最终版 |

**【判据】** 双写仓库的冲突面，靠「**物理隔离 + 时序纪律**」控制，不靠「小心」。

**【教训·具体】** 带未提交改动直接 rebase 会拒跑；`GIT_EDITOR=true` 用来跳过卡住的编辑器。

### 3.1.3 push 结果必须用退出码判断

**【事实·可复现】** MEMORY 原文：**禁 `git push | grep error`**，用退出码；push 后 `git fetch && git rev-list --left-right --count HEAD...origin/main` 核对 **`0 0`**。

**【教训】** 曾出现「push 报 lock error 但其实远端已经是我的提交」的**竞态**——再次 fetch 才发现远端已前移。**判断推送是否成功，不能靠输出文本，要靠远端 ref 的实际状态。**

### 3.1.4 临时脚本的三个坑

**【事实·可复现】**

1. **路径命名**：改写 `data.json` 一律用**工作区内唯一文件名**。曾因 `/tmp/update_data.py` 残留旧脚本被误执行，把 `data.json` 覆写成两天前的状态 → 只能 `git checkout -- data.json` 恢复。
2. **幂等性**：prepend 日志的临时脚本要加 `if MARK in note: sys.exit(1)` 防重复叠加；重跑前先 `git checkout HEAD -- data.json`。
3. **校验方式**：JSON 合法性**只靠 `json.load` 是否抛错**。曾自作聪明加 `assert "\n" not in note` 报错——实则 `json.dump` 会把换行转义成字面 `\n`，读回来当然含真换行。

**【可迁移性】** 高。**「用生成器改数据」这件事本身很危险**，需要三道锁：唯一文件名、幂等标记、先备份后改。

### 3.1.5 GitHub Pages 的四种故障模式（全部真实踩过）

**【事实·可复现】**

| # | 故障 | 判别点 | 应对 |
|---|---|---|---|
| 1 | Jekyll 管线损坏 | 构建 duration=0 秒挂 | 切 `build_type=workflow` 走 Actions |
| 2 | `deployment_queued` 超时 | 排队约 10 分钟后 Timeout | **`git commit --allow-empty` 造新 SHA** |
| 3 | `Set up job: Service Unavailable` | 失败在 Set up job 阶段 = 平台侧故障 | `gh run rerun <id>` |
| 4 | 卡死的 in_progress 阻塞后续 | `Please cancel XXX first` | 先 cancel 旧 run |

**【根因·关键】** 故障 2 的解法之所以是「造新 SHA」，是因为 **Pages 部署 ID 就是 commit SHA，被 cancel 过的 SHA 重发会立刻再次 cancelled**。这个机制不写在文档里，只能踩出来。

**【教训·高危】** 曾执行 `gh api -X DELETE .../pages` 重置 Pages → 已发布产物被清空、**站点 404 约 8 分钟**、无回滚路径。**这类操作非必要不做。**

### 3.1.6 网络与环境类踩坑

**【事实·可复现】**

- Git Bash 里 `git push` 挂死 = **GCM 卡 GUI 登录** → 改用 PowerShell 工具直推即成功。
- Git Bash 里 `curl` 直连 `raw.githubusercontent.com` **挂死 3 分钟** → 改用 PowerShell `Invoke-RestMethod` + 代理 `127.0.0.1:7897`。
- 要下载到**仓库内**再删（`/tmp` 在 Windows 版 Python 里看不到）。
- 临时文件被占用删不掉 → 先 TaskStop，再用 Python `os.remove`。
- GitHub push 偶发 `Empty reply from server` / `SSL_ERROR_SYSCALL` → **原样重试一次即成功**，无需改配置。

**【判据】** 网络类报错先判「是瞬时抖动还是配置错误」——**同一个命令原样重试一次，是最廉价的判别实验**。

### 3.1.7 并发写的物理隔离

**【事实·可复现】** `video.json` 独立于 `data.json`，由另一台机器单独写。

- 理由：另一台机器**整文件重写** `data.json` 时根本碰不到 `video.json`，央视主页面零风险。
- 效果：视频功能上线至今，`data.json` 从未因它出过问题。

**【判据】** 两个写入方，就不要写同一个文件。**隔离一个文件，胜过加十条纪律。**

## 3.2 测试与验证经验

### 3.2.1 ⭐ 测试禁写死任何会随时间变化的东西

**【事实·可复现】** 三次翻车：

| 写死的东西 | 翻车方式 |
|---|---|
| `2026-09-11` 当「3 天后」 | 日期推进后变「后天」→ 模块隐藏 → 误报失败 |
| 淘汰名单「王艺迪/蒯曼/黄友政」 | 陈垣宇出局后立刻误报失败 |
| `stageFixtureData` 硬编码 `2026-09-13` | 日期推进后落入 past → `buildAbove` 为空 → 脆弱测试 |

**【判据·已固化】** 「名册人数 / 性别 / 淘汰名单 / `nextEvent.date` / fixture 日期」一律以**真实计算函数的结果**为唯一事实来源动态推导，并断言不变量（如「存活 + 淘汰 = 总人数」）。

**【更深一层·重要】**

- **「测试期望过期 ≠ 代码错了」**：淘汰判定本身是对的，是测试硬编码过期 → **改测试，不改代码**。
- **判「今天」必须用本地日期拼接，禁 `toISOString().slice(0,10)`**——UTC 比北京晚 8 小时，凌晨 `00:0x` 会取到「昨天」，把今天误判为可见空窗天。

### 3.2.2 样本必须来自真实数据

**【事实·可复现】** 项目两个**潜伏 bug 只有真实数据才复现**：

- 「头号种子抽成『世界第』」——只有真实 `note` 的特定句式才触发；
- 第二个 bug 在 **rebase 到采集端新数据后**才复现。

**【判据·已固化】** `tests/README.md` 原文：「样本优先用真实的。臆造的样本容易『测试通过但线上翻车』。」

### 3.2.3 ⭐ 验证要按调用方溯源

**【事实·可复现】** 一次**差点误报「采集端契约不匹配」**：

- 用 `renderItemListHtml(..., day.schedule)` 直接喂 `data.json` 的数组 → 输出满屏 `undefined`。
- 实际是**调用方式错了**：`renderItemListHtml` 读 `it.program`，那是给 `parseNoteToItems`（前端解析产物）用的；真实 `day.schedule` 走的是 `renderScheduleContent`（读 `content`/`tournament`）。
- **两条链路都正确，是验证脚本用错了 API。**

**【教训·已固化】** 「渲染链路要按调用方溯源，不能拿底层渲染函数喂原始数组下结论；**dump 真实 HTML 回读才是硬证据**。」

**【可迁移性】** 极高。这是 AI/人做验证时最容易犯的错——**用一个函数跑通了就下结论，没确认它是不是生产路径上的那个函数**。

### 3.2.4 分层自检：解析层 + 渲染层

**【事实·可复现】** 项目固化的自检两层：

1. **解析层**：`api.parseDayNote(day.dayNote)` 检查要点数、最长字数、括号配对、next 是否抽出。
2. **渲染层**：`api.buildAbove(api.prepareCtx(d,{now})) + api.buildBelow(ctx,d)` 数 `<section>` 数、关键词命中。

**【教训·关键】** 「**单看 `parseDayNote` 正常不代表页面正常**，中间还隔着 `dayHasContent` 折叠判定」——项目正是靠渲染层自检发现「四天全消失」的。

**【可迁移性】** 高。**流水线有多层，就要在每层出口设检查点**。

### 3.2.5 视觉验证：CDP，不是 `--screenshot`

**【事实·可复现】**

- `--screenshot` 与 `--dump-dom` 在该 Chrome 版本**不可靠**（截图宽度与真实视口不匹配 → 误判「页面横向溢出」；dump 输出为空）。
- 可靠姿势：`--headless=new --no-sandbox --remote-debugging-port=9333` 常驻，用 Node 内置 WebSocket 连 CDP，`Emulation.setDeviceMetricsOverride` 精确锁视口 → `Runtime.evaluate` 量 `scrollWidth` → `Page.captureScreenshot` 截单卡。
- **判断「是否溢出」以 `documentElement.scrollWidth === clientWidth` 为准，不要凭截图右边缘被裁就下结论。**

**【可迁移性】** 高。**工具会骗人，要用可证伪的度量代替肉眼判断。**

### 3.2.6 测试跑法与护栏

**【事实·可复现】**

- `node --test tests/logic.test.js tests/render.test.js tests/data-contract.test.js`（**必须显式列文件**；`node --test tests/` 会 `MODULE_NOT_FOUND`）。
- 项目在单测里加了**防回归护栏**：断言存活面板 HTML **不得含裸 `class="player"`**（因为曾撞类名导致布局全乱）。
- `tests/` 全程只读，无任何 `writeFile/mkdir/rmSync/unlink` 调用 → 跑测试不改仓库。

**【判据】** 每一次「血的教训」修完后，都应该变成一条**护栏断言**，而不是一条记忆。

## 3.3 数据真伪判定经验（领域知识，重写必须带走）

### 3.3.1 ⭐⭐ 结论与依据分开判定

**【事实·可复现】** 9/3 采集端判定「王楚钦退出澳门站」传闻**不实**并整稿不采，依据是：① 只有主播口播；② 文中把亚运写成「杭州亚运会」（实为日本爱知·名古屋）。

**9/4 WTT 官方证实：王楚钦确实因伤退赛。**

**【教训·已固化为铁律】** 原文：「该稿**依据与基础事实仍错，但结论对**；此前连结论一并否定属**推断过度**。」

> **铁律：依据错只否定依据，结论仍需另行求证，不得连坐否定。**

**【可迁移性】** 极高。**信息核验的通用方法论**。

### 3.3.2 ⭐ 数源要数「独立编辑/独立域名」

**【事实·可复现】** 两次翻车：

1. 曾把「腾讯 13:55 / 网易 19:40」当两个独立源——实为**同一篇早间前瞻稿同时发布在 `new.qq.com` 与 `163.com`**，属同稿跨平台转载，**不构成独立源**，且整套时间与官方 OOP 全不符 → 整体剔除。
2. 「泊雷特三源」实为**腾讯一稿 + 网易转载**，只有 1 个独立源。

**【判据·已固化】** 「**『多数稿一致』可能只是同一稿系被多家转载**，数源数要数独立编辑/独立域名。」

**【操作化】** 遇到多域名给出**同一组异常时间/异常细节**时，先比对标题与正文是否同稿，再决定计数。

### 3.3.3 ⭐ 结构性校验：用赛制/签表反证事实

**【事实·可复现】**

| 校验法 | 案例 |
|---|---|
| **分区表反证对手** | 「种子在首轮轮空」→「A 是 X 区种子」与「A 是某人首轮对手」**不能同时成立**。据此把李天阳对手由「泊雷特」更正为「力廉·巴德」 |
| **淘汰反证串位** | 「已被淘汰的对手不会出现在下一轮」→ 混双 1/4 的对手被写成他们 1/8 淘汰过的人 → 判串位 |

**【判据·已固化】** 判断「某人首轮对手是谁」时，**优先用官方分区/签表做结构性校验**，而不是数票。

**【可迁移性】** 高。**任何有内在约束的领域（赛制、时间线、地理、物理），都能用约束做交叉验证，这比数源更硬。**

### 3.3.4 冲突处理三原则

**【事实·可复现】**

1. **比分顺序先做镜像校验**：各源局分顺序相反 = 胜者/负者视角差异，**不是冲突** → 统一取胜者视角。
2. **时刻取多数（众数），少数派留痕**。
3. **量化数字打架只写定性**（如「训练时长 20~25 天 / 约一个月 / 约 30 天」三说 → 维持模糊）。

**【补充·已固化】** 「大比分打架以**逐局列表**为准」；「矛盾先查是否**描述不完整**」（德甲「4 人打赢 3 场」与五盘三胜冲突 → 实为漏了第 5 盘，判描述不完整而非矛盾）。

### 3.3.5 五类幻觉稿的识别标记

**【事实·可复现】** 项目累积识别出五类不可信稿：

| 类型 | 识别标记 | 实例 |
|---|---|---|
| **旧闻翻新** | 内容与官方名单/赛制/赛历冲突；「X 去哪看回放」体裁的服务稿 | 把 7/18 全锦赛混双当今日热点 |
| **预写稿/幻觉** | **赛前就写出赛果**，或写「凌晨进行」 | 搜狐在赛前发出德甲赛果 |
| **标题党** | 标题「XX 力克 YY」但正文是「如果…就…」式前瞻 → **必须读正文** | 「周启豪力克张本智和」实为前瞻 |
| **AI 体例聚合稿** | 「结论:」式、无一手源、跨区乱配 | 公众号「X日X点 A vs B」清单与官方签表冲突 |
| **时差误算稿** | 把北京时间当当地时间（或反之） | 「17:00 德国时间 = 北京 23:00」 |

**【三连判据·已固化】** **无官方源 + 多稿自相矛盾 + 细节夸张 = 直接排除。**

**【反向判据·同样重要】** **单一平台多稿自相矛盾 ≠ 事件本身为假**，应追加跨平台（含地方官媒/公众号）复核再下结论。（邓亚萍杯案：先判假，后经跨平台复核确认真、但央视不转播。）

### 3.3.6 命中即判错的具体标记（领域知识）

**【事实·可复现】** 以下任一条命中，该稿直接判错：

- 亚运写成「**杭州亚运会**」（2026 实为日本爱知·名古屋）
- 澳门站名单出现**温瑞博/向鹏/林诗栋**（已退赛或不在列）
- 「**537 万 / 2000 积分**」→ 这是**大满贯**口径，不是冠军赛
- 同稿内时差 ≠ 6 小时
- 场馆名错（把澳门写成「塔石体育馆」，实为东亚运动会体育馆）
- 「WTT 冠军赛需从资格赛打起」→ 冠军赛 32 人正赛**不设资格赛**

**【可迁移性】** 中（领域强相关），但**「建立领域内『命中即判错』清单」这个方法本身可迁移性极高**。

### 3.3.7 源的权威优先级与分层

**【事实·可复现】**

**权威优先级**：央视网/奥林匹克频道 > @WTT世界乒联 > 新华社 > 腾讯/搜狐/体坛周报。

**按字段分层判源**（9/15 定案）：

- **关键事实**（有没有这场、对手是谁）→ 要 **4 源**；
- **次要事实**（几点开打）→ **2~3 源**即可，按规范照写并加证据提示；
- 只有「连对手都没定」或「时刻仅 1 源」才留空。

**【教训·关键】** **「上一轮源数不足」不是永久结论，每轮必须从零重数。** 9/17 01:11 轮还只有 1 源，09:45 轮就冒出三个独立域名 → 立即写入 19 场。

### 3.3.8 黑名单与版权铁律

**【事实·可复现】**

- **黑名单**：`sports.sina.com.cn/pingpang`、`sports.163.com/pingpang`、`s.weibo.com`、`so.toutiao.com`、`sports.sina.cn` 首页聚合稿、`k.sina.cn`、`cnyouth.com`（错时间戳/旧稿）、网易号「乒乓乐园」、搜狐特定 ID。
- **版权铁律**：腾讯体育 / 爱奇艺 / 优酷 / 抖音 / B站 对多数国乒大赛**无直播版权**，其时间信息多为转载，**不能当直播时间验证源**，只能作新闻线索。
- **官网抓取坑**：`sports.cctv.com/epg?channel=X&date=Y` 对 CCTV-5 与 CCTV-16 会**间歇性丢弃参数**返回默认页 → 改用 `sports.cctv.com/epg/index.shtml?channel=X&date=Y`；判别法＝看返回条目链接是否保留了参数。
- 电视猫 CCTV-5+ 的 slug 必须是 `CCTV-CCTV5-PLUS-wN`（写 `CCTV5PLUS` 会错返 CCTV-1）。

## 3.4 产品与需求经验

### 3.4.1 适老化的经验

**【事实·可复现】**

- **`html{font-size:18px}` ≠ 字号达标**：`clamp(.85rem…)` / `.7rem` 让实际渲染值远低于 18px（实测 124 条声明中 65 条 <18px；449 个文本节点中 **62% <18px**）。
- **对比度、触控、动效三项做对了**：对比度 4.93:1~16.5:1 全过 AA；触控全部 ≥48px；`prefers-reduced-motion` 已处理。**问题只在字号。**
- **首屏比字号更重要**：存活面板占 57% 首屏，把第一场比赛时间推到 1.15 屏。
- **文案要去技术词**：断网时页面直接显示 `数据加载失败(Failed to fetch)`。
- **「留空会被前端当成『未评估』，外婆分不清」** → 采集规范强制「无冲突也明示」写 `✅低风险`。**这是一条很好的适老化洞察：对老人而言，「没写」和「没问题」不是一回事。**

**【判据·已固化】** 「不要大段文字」「一句话说清」「台号写 `央视5` 不写 `CCTV-5`」「禁用内部行话（如『转播段尾部截断型』）」。

### 3.4.2 文档纪律经验

**【事实·可复现】**

- **同日多轮早报用「一日一档覆盖更新」**：一天只保留一个 `YYYY-MM-DD.md`，第二轮起覆盖并在头部标注「首轮 HH:MM / 最新复核 HH:MM」，**不新建带时刻的文件名**。
- **改了 `nextEvent.note` 的定案，必须回头同步四天 dayNote 的名单句**（曾只改 note 未改 dayNote → 页面出现矛盾数据）。
- **昨日战报原样保留**：昨日块一字不改（昨日空窗天不渲染，改了也白改）。
- **「昨日空窗天不渲染战报区」→ 昨日的重要战报必须在今日 dayNote 复述一遍**（否则页面上看不到）。

### 3.4.3 ⭐ 「让数据端配合前端写法」是反模式

**【事实·可复现】** memory 里有一批规则，读起来是「数据写作规范」，实际是**前端解析器脆弱性的外溢**：

| 规则 | 它真正在防什么 |
|---|---|
| 「名单句在前、`背景:` 断后」 | `parseNextRoster` 的 lookahead 收不住，会把整段日志当缺席名单（实测 absent=**39~82 条垃圾**） |
| 「`nextEvent.note` 追加文本**禁用 `→`**」 | 含 `→` 会被归入 schedule 段走时间线分支，`next__lines` 消失 → 测试挂 |
| 「dayNote 首句必须是短结论」 | `parseDayNote` 的 `cut > 3` 判断：首句若形如「9/1(周二)…」，左括号落在索引 3 → `3 > 3` 为假 → 退化成长句 |
| 「出战段必须以 `背景:`/`赛程:` 收尾」 | 同上，首次句号收尾会把后续内容吞进最后一个人名 |
| 「已填 result 必须移除 risk」 | 前端两条分支互斥，同时存在会渲染冲突 |
| 「要点最长 ≤100 字」 | `parseDayNote` 的分句规则 |
| 「risk 禁写『电视看不到』类词」 | `riskSaysNoTV` 会把**整场从页面删除** |
| 「`stage` 里可以写赛制，前端会拆层」 | 前端已具备拆层能力，这条是**正向的**（例外） |

**【教训·已固化】** 「修前端解析问题**优先在采集端改写法**，不动 app.js。」

**【主理人评注】** 这条策略**在短期内是对的**（改数据比改代码风险低），**但长期是错的**——它把「解析器的脆弱性」永久转嫁给了数据作者，形成**双向耦合**：改数据要懂前端，改前端要懂数据。`tests/README.md` 自己都登记了「已知限制：将来若采集端改句式需同步补关键字」。

**【重写要做的】** 把这些规则**从「写作规范」降级为「历史注脚」**，用结构化字段替代（见 §5.3）。

## 3.5 前端解析与渲染经验（血泪清单）

### 3.5.1 根本原则

**【判据·已固化】** 原文：「**任何 note 渲染前必须过解析器结构化，禁止 `esc(原文)` 直出**；解析失败走原文 fallback。」

**【判据·补充】** 「解析失败兜底：返回单 chips 字段缺失的对象，看空就走原文 esc，**不破不立**」——即**任何解析器都必须有 fallback，绝不让卡片消失**。

### 3.5.2 解析器的具体坑（逐条可复现）

| # | 坑 | 表现 | 根因 |
|---|---|---|---|
| 1 | **lookahead 收不住** | 缺席名单吞掉整段日志（absent=39~82） | `[,;。]\s*(出战\|国乒\|赛程\|背景…)` 无匹配时一路吞到底 |
| 2 | **括号位置敏感** | lead 退化成长句 | `cut > 3` 判断 + 首句左括号在索引 3 |
| 3 | **传参类型** | `roster = 0` | `parseNextEventNote(data.nextEvent)` 传对象 → `String(obj)` = `"[object Object]"`，**必须传 `.note` 字符串** |
| 4 | **字段名** | 自检得 0，误判「名单没解析出来」 | 名单挂在 **`roster`**（`roster.squad`/`roster.absent`），不是 `nextSquad`/`nextAbsent` |
| 5 | **禁用字符** | 测试挂（`next__lines` 消失） | `→` 触发时间线分支 |
| 6 | **前缀识别不全** | 出战名单长期为空 | 只认 `出战[:：]`，真实数据用「国乒9人」→ 补 出战/国乒\d*人/报名/参赛/阵容 |
| 7 | **子串匹配过宽** | 陈幸同误显 🇩🇪、汉娜·高达误显 🇧🇷 | 从 `info`（描述文本，会提及对手国）子串抓国名 → **必须用 `nation`**；`info` 仅精确匹配国别组合段 |
| 8 | **键序短路** | 港澳台全变 🇨🇳 | `FLAGS` 里「中国」排在「中国香港/澳门/台北」之前 |
| 9 | **分类关键词过宽** | 羽毛球被混进「乒乓节目」 | 乒乓正向词含「决赛/锦标赛/录像/单打/双打/世界杯」——**这些词羽毛球也用** → 改「负向优先 + 正向收紧 + 默认其他」三级 |
| 10 | **计数口径** | 「女单 · 12 人」（真实 10） | 双打组合被当选手、日志尾巴被当人名 |
| 11 | **模块被误隐藏** | 下一站卡整段消失 | `applyFilter` 只认 `.match`/`.day__pending` → 需补 `.day__next` 守卫 |
| 12 | **折叠误杀** | 「今天完全空白」 | `dayHasContent` 漏认新加的 `dayNote` → 纯 dayNote 的天被判真空档 |

**【共同点】** 12 条里有 **9 条**是「解析器的宽容度不足或过度」造成的。**这是「用自然语言当数据接口」的必然代价。**

### 3.5.3 CSS 与布局经验

**【事实·可复现】**

- **类名铁律（血的教训）**：新增样式前**必须先 grep 类名是否已被占用**；新增样式一律带模块前缀。首版存活面板裸用 `.player`，撞了比赛卡选手列 → 卡片选手名被加边框/padding/`nowrap` → **文字溢出、布局全乱**。
  → 事后在单测里加了护栏：**断言存活 HTML 不得含裸 `class="player"`**。
- **`min-width:0` 是 flex 收缩换行的关键**：flex 项默认 `min-width:auto`，文本无法收缩换行 → 窄屏「一字一断」。
- **`position:sticky` 会被 `overflow:hidden` 截断**：`.day` 去 `overflow:hidden` 才能让 `.day__head` 吸顶。

**【可迁移性】** 极高。**「全局 CSS 没有命名空间」是这类零构建项目的结构性缺陷。**

### 3.5.4 渲染层的顺序与互斥

**【事实·可复现】**

- **`schedule` 只在 `matches` 为空的 else 分支渲染** → 有 `matches` 的日子加 `schedule` 是**死内容**。推论：「某日部分对阵待定时**宁可留 `schedule`**，别只写已定的几场 `matches`」。
- **渲染优先级**：`result` > `live` > 待开赛。
- **已填 `result` 必须移除 `risk`**（互斥）。

**【可迁移性】** 中。**「两个字段互斥」这种隐性契约，是契约设计缺陷的信号**——应该用一个 `status` 字段而不是「有没有填某字段」。

## 3.6 记忆系统本身的元经验

### 3.6.1 ⭐ 记忆会被注入上限截断

**【事实·可复现】** memory 里反复出现：

- 「MEMORY.md 超限被截断（16287B），已重写压到 14926B（**仍偏大**）」
- 「**首次重写反而变大**（17108 字符），二次压缩后回落」
- 「原 16245 字符超限被截断，已合并去重重写为 ~5.5K」
- 一天之内出现 3 次压缩（06:16 / 14:16 / 22:16 轮各一次）

**【教训】** 记忆不是越全越好。**必须有分层和淘汰机制**：

- 铁律 → 留在 `MEMORY.md`
- 判据 → 留在 `MEMORY.md` 的判据段
- 细节 → 外置到 `前端自检细则.md`（项目已经这么做了，并注明「避免 MEMORY.md 超限被注入截断」）
- 流水账 → 留在当日 `YYYY-MM-DD.md`

**【可迁移性】** 极高。**这是所有长期运行 agent 的通病：记忆膨胀 → 截断 → 关键判据丢失 → 重犯旧错。**

### 3.6.2 ⭐ 判据会过期，且会形成路径依赖

**【事实·可复现】** 项目自己总结出的判据：

> 「以『官方旧名单』否定『新事实』时，要标注名单的发布时间；**赛事临近时名单会更新，旧名单的否决力会衰减，需每轮重估、不要形成路径依赖**。」

**【事实·具体案例】** 亚运男双配对**复核了 8 次**，来回翻案 3 次（林诗栋/温瑞博+黄友政/向鹏 → 林诗栋/黄友政+向鹏/温瑞博 → 回退）。每一次翻案都有新证据，说明「官方原文」本身也在变。

**【可迁移性】** 极高。**「上一轮的结论不能沿用」应当写成显式规则**，而不是靠人记得。

### 3.6.3 记忆里混着过期内容

**【事实·可复现】** 重写计划启动时，`MEMORY.md` 里仍有：

- 「Gitee 备份仓库」（8/9 已弃用）
- 「全部/国乒/日韩筛选」（9/11 已删 UI）
- 「前端自检细则见 app.js:1975-2008」（实际已漂移到 2071）
- 「当前窗口状态（9/17 起）」（已是 9/27）

**【教训】** **记忆需要「过期标记」机制**，不能只靠人工重写。可行做法：每条判据带一个「最后验证日期」或「适用条件」。

# 第 4 部分 · 重写方案

## 4.1 六条重写原则

1. **需求先行**：先冻结两份 PRD，再动一行代码。
2. **判定与展示分离**：**任何业务判定不得依赖自然语言**。散文只能进「展示区」，不能进「逻辑区」。
3. **契约优先 + 双写过渡**：采集端是另一台机器，无法同步上线。新字段**先加法**，前端「结构化优先、散文回落」，验证一致后再切。
4. **零构建保留**：真实约束是「Pages 整仓上传、无 CI 构建」。用**原生 ES module** 即可拆文件，无需 npm / 打包器。
5. **删掉解析器是重写的最大红利**：MVP 不含任何 `parse*` 函数，可直接砍掉约 1000 行。
6. **业务规则以清单+测试迁移**，不以代码迁移。
